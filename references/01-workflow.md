# 01｜操作手册：从一个品类到一个投入决策

## 先分清三种结构

**判断结构**：一个最终决策 → 三个板块 → 六个维度。

**执行顺序**：设计研究 → 搜集与验证证据 → 形成商业判断 → 审计与交付。

**证据结构**：来源 → 原子判断 → 维度结论 → 板块判断 → 最终决策。

不要把执行步骤当作新的分析维度，也不要让所有研究字段挤进正文。复杂性应该保存在可追溯的工作底稿里。

每一步都遵循：**明确要回答的问题 → 选择能够回答它的工具 → 记录证据 → 说明还不知道什么 → 决定下一步。**

---

## 阶段一：研究设计

### 步骤 1｜锁定对象、边界与公司条件

**输入**：用户任务、相关对话、已授权的公司资料、实际可用工具。

**操作**

1. 把品类写成一句可检验描述：谁，在什么情境下，遇到什么问题，通过什么产品形态获得什么价值。
2. 将“我们要验证是否值得投入”与“已经决定做产品，寻找支持理由”区分开。默认采用前者。
3. 明确纳入和排除的产品。例如研究读书 APP 时，先区分电子书阅读、摘要、有声书、阅读器工具；可以做相邻市场比较，但不能混算规模。
4. 分开记录地区、语言、平台和客户类型。企业客户与消费者、国内与海外、iOS 与 Android 不是天然同一市场。
5. 阅读公司能力、渠道、资产和预算信息。缺少时设置 `company_context_status=unknown`，后续只给条件性匹配判断。
6. 列出会改变研究方向的约束：是否可做内容供给、是否有版权、是否能接触特定渠道、是否允许医疗相关功能等。约束的法律含义另行查官方资料，不能自行猜测。
7. 盘点工具。记录可联网与否、可读取哪些内部资料、是否可执行代码、是否有已授权行业数据、是否能浏览登录后页面。未调用成功前不把数据源记为可用。
8. 建立工作目录，将时间写成明确日期；启动前用宿主真实日期核验，不把示例日期直接抄进来。

**默认处理**

若输入仅为“研究某 APP 品类”，先用明确的临时范围推进。涉及两个可能市场时，先做有限对照扫描，再选择本轮重点并说明原因。不要无边界地研究全球所有市场，也不要因为用户在某个国家就推定产品面向该国家。

**产出**：`brief.json`，包含范围、假设、公司信息状态、工具与授权。

**完成条件**：下一位 Agent 能独立解释本轮研究什么、不研究什么、未知哪些条件。

### 步骤 2｜建立问题树、证据需求与研究优先级

**输入**：`brief.json`。

为六个维度各设少量高价值问题，而不是一开始列几十个指标。以下是默认问题，不要求逐字照抄。

| 维度 | 决策问题 | 候选证据 | 主要误判 |
|---|---|---|---|
| D1 人群覆盖 | 谁有需求，其中多少可以实际服务和触达？ | 行为调查、目标群体规模、产品活跃与渗透证据 | 用总人口或相邻大行业替代本品类 |
| D2 需求强度 | 用户目前付出什么时间、金钱或迁移成本？ | 重复使用、现有付费、主动寻找替代、任务失败场景 | 用表达兴趣代替实际行为 |
| D3 实现难度 | 最小有效解决方案需要什么，难点在哪里？ | 产品流程、依赖、服务交付要求、专业与合规限制 | 把能做界面当成能实现价值 |
| D4 能力资产 | 哪些关键条件已有证据，缺口如何补？ | 内部人员、渠道、合同、数据、案例 | 根据泛泛公司描述虚构优势 |
| D5 商业玩法 | 谁付钱，为什么付，是否有更好的收入或成本结构？ | 价格、付费边界、变现结构、渠道与交付方式 | 把新功能当成新商业模式 |
| D6 运营竞争 | 同一经营单位下，收入能否覆盖获取和服务成本？ | 同口径转化、留存、成本、竞争和替代分析 | 拼接不同人群和周期的数据算账 |

为每个问题分配 ID，例如 `Q-D2-01`，并记录：

- 当前假设、可能推翻它的证据。
- 最适合的指标与口径；找不到可靠指标时如何定性。
- 优先级：决定性、支持性、背景性。
- 预计来源类型和下一步检索动作。

优先级不是由“资料好不好找”决定，而是由**结论答错是否改变投入决策，以及补查能否减少这种不确定性**决定。不要为了看起来科学，给这种优先级强行乘出一个无依据的数值。

**产出**：`research_plan.md`。

**完成条件**：每个拟查资料都有对应决策问题；每个决定性问题都准备了反证方向。

## 阶段二：证据研究

### 步骤 3｜宽搜，建立市场地图和研究样本

**输入**：问题树。

**操作**

1. 搜索品类常用名称、本地语言名称、相邻词和用户任务词。陌生名词先核验含义。
2. 找直接竞品，再找跨品类替代、免费工具和人工服务。不只搜索标题包含品类名的产品。
3. 将竞争供给分成有解释价值的类型：例如通用工具、垂直细分、订阅服务、免费替代。类型由实际供给决定，不强行凑齐。
4. APP 默认选取 5—8 个代表样本；集中市场可以更少，分散市场可以增加。说明选择依据及未覆盖范围，不称其为完整市场。
5. 确认品牌、开发者、商店 ID/包名、地区页面。一个品牌可能有多个产品，产品也可能改名。
6. 记录当前定位和观察日期。功能表仅作供给线索，不把商店文案当成真实体验。
7. 如能合法访问实际产品，可以核验关键路径；只有网页资料时写“基于公开页面”，不得声称已经安装、试用或完成支付。

**产出**：`competitors.jsonl`、一段品类定义与竞争格局初判。

**完成条件**：知道主要解决方案类型和重要替代物，可以开始深查，而不是声称已穷尽市场。

### 步骤 4｜定向检索与原始证据核验

**输入**：高优先级问题、竞品样本、工具能力。

按五条证据线推进，不要求固定顺序：

**用户线**：谁采用、频率如何、为什么选择或放弃、是否已经付费。优先行为数据，再用访谈和评论解释原因。

**供给线**：产品当前卖什么、免费与付费边界、实际价格、地域差异、替代方案。保存观察条件，避免把不同套餐混成价格区间。

**经营线**：收入定义、获客渠道、转化、留存、变动成本、服务负担。融资额、估值与收入是不同事实。

**可实现线**：最小方案的关键依赖、供给、技术与运营要求、必要的效果或专业证据。

**公司线**：内部已有渠道、人员、资产、服务能力和经营数据。使用授权连接器或文件读取，禁止通过公开搜索提交内部敏感资料。

每获得一条关键资料，立即执行一个小闭环：

```text
问题 ID → 检索 → 打开原文 → 找到对应段落/表格 →
核对口径 → 创建来源记录 → 写原子判断 → 标注局限 → 更新问题状态
```

**原子判断**是一句可单独证实或证伪的陈述。不要在同一条记录里写“用户很多、需求强、增长快、竞争弱”四个不同判断。

搜索结果只作为候选。读不到正文时保留 `lead_only` 或失败状态，不因为摘要给了数字就升级成已核验事实。对 PDF 图表，查看原页并核对标题、坐标、脚注和样本；不是只复制提取后的数字。

评论研究建议先定义抽样范围和目的，例如“近六个月、两个商店、覆盖不同评分层级，探索中断原因”。方便样本能帮助产生假设，不能据此宣称某比例的全体用户都存在该问题。将原文最小必要片段、时间、评分和主题编码分开记录，避免保存不必要的个人身份信息。

**产出**：`actions.jsonl`、`sources.jsonl`、`claims.jsonl`；必要时保存许可范围内的证据截图或数据片段。

**完成条件**：决定性问题已有可定位证据，或已记录为什么拿不到及其后果。不是所有问题必须找到数字。

### 步骤 5｜统一口径、去重、处理冲突与置信度

**输入**：来源和判断台账。

逐条检查：

1. **人群与地域**：成年人还是全部人口？一个国家还是全球？抽样调查能否代表目标群体？
2. **时间**：报告发布日期、数据统计期、事件发生期、实际访问日分别是什么？
3. **指标**：下载、活跃、注册、付费、销售额、净收入、ARR 分别是什么？是否累计？
4. **单位与分母**：币种、税费、月/年、每下载/每注册/每付费用户是否一致？
5. **来源独立性**：不同页面是否转述同一家公司或同一份数据？
6. **证据性质**：直接记录、公司自述、样本估计、模型外推、商业假设还是分析推断？

发生冲突时，不立刻选择更大或更新的数字。先建立冲突记录，确认是否相同定义，再看原始证据、方法和时间差。无法解决时保留并列区间或明确“无法比较”，解释对决策的影响。

每个重要判断使用高/中/低/未评估置信度，并写理由。**对“某公司声称某收入”的高把握，不等于对“该收入已独立验证”的高把握。**

**产出**：可比较的判断台账、冲突说明和置信度。

**完成条件**：综合判断不会依赖被混算的数字、重复来源或被隐藏的推算。

## 阶段三：商业判断

### 步骤 6｜压缩为六个维度结论

每个维度输出以下结论卡，详细证据保留在底稿。

```text
维度：D2 需求强度
一句话结论：……
关键依据：C012、C018；其中 C018 为来源方自述。
可量化部分：……；无法量化部分：……
置信度与限制：中；因为……
对最终决策的影响：支持/削弱/尚未改变……
尚未解决的问题：……
```

检查相邻维度的区别：

- D1 是覆盖范围；D2 是需求和行为强度。人多不自动等于需求强。
- D3 是客观实现要求；D4 是公司与这些要求的差距。
- D5 是收入、获客与交付的机制；D6 是这些机制在竞争和成本条件下能否持续。

形成三个板块判断，但不要跳过缺证据的 D4。公司情况未知时，应写：“品类层面允许低成本试验；公司适配性取决于尚未确认的渠道/内容/专业资源。”

**产出**：`dimension_assessments.json`。

**完成条件**：只看六张卡片，能够理解哪些因素支持投入、哪些削弱投入、哪些仍未知。

### 步骤 7｜建立最小经营模型，反算成立条件

**输入**：商业模式、已核验价格和费用、成本与转化证据。

1. 先定义一个经营单位：每个下载、每名付费用户、每个企业合同、每笔订单或每单位内容。
2. 确定收入口径与周期，再匹配同周期成本。现金回款与会计利润分开。
3. 将模型输入分成实测、外部参照、估算和待验证假设；不能把示例数值悄悄变成预测。
4. 选择少量对结果敏感的变量，构建保守、基准和较好情景；情景是条件分析，不是发生概率。
5. 缺获客或留存数据时，反算盈亏平衡所需水平，再判断这个水平有什么证据支持。
6. 若经营账依赖“未来续费很好”“自然流量免费”等假设，单列风险。
7. APP 可以使用附带的订阅示例计算器；其他商业模式改用对应公式，不硬套。

**产出**：`unit_economics.json` 和可复算结果；或其他品类同等结构的模型文件。

**完成条件**：读者能追踪每个输入来自哪里，知道什么条件下结论会翻转，而不只是看到一个漂亮利润数。

### 步骤 8｜反证与综合判断

提出一个最强反对意见，而不是写无关紧要的“可能存在风险”。例如：

- 产品解决的是低频问题，没有持续订阅理由。
- 免费替代已经足够，付费功能没有可验证增量。
- 头部有收入，但来源于我们不具备的渠道、品牌、内容或服务能力。
- 客户需求存在，但销售周期和服务成本使当前预算不可承受。
- 效果承诺没有足够专业证据，或验证本身会触及不可接受的风险。

为每个反对意见查证，标为支持、削弱、未解决。没有找到反证不是证明反证不存在，必须看是否真的搜索了最可能出现它的地方。

综合时回答：

```text
机会的成立理由是什么？
公司可以用什么具体切口去验证？
哪个尚未解决的假设最可能改变结论？
能否用范围受控的验证包获得足够有价值的信息？
```

**默认不输出机械综合分。**若用户明确要求评分，先设锚点和权重，区分吸引力与证据质量，说明权重变化是否改变排序；不得让多个普通优点把决定性的不可行条件“平均掉”。

**产出**：决策草案、反证清单、关键敏感因素。

**完成条件**：结论不是材料多数表决，也不是对最初假设的辩护。

## 阶段四：决策交付

### 步骤 9｜把剩余未知转成最小验证包

只设计能够改变下一次决策的试验。不要把完整产品开发、所有渠道测试和多个变现模式塞进一个“最小包”。

通常按以下顺序减少不确定性，顺序可依品类调整：

**问题是否真实 → 是否愿意采用或迁移 → 是否真实付费 → 是否获得持续价值 → 是否能以合理成本触达。**

这不是要求每次跑完五个试验。选择当前最薄弱、最重要、最适合验证的一到三个问题。

用 `validation_package.md` 写清：假设、对象、排除条件、最小交付、对照方式、主指标、分母、窗口、价格、样本依据、预算上限、停止条件、责任人和风险审核。

说明哪些是建议、哪些是实测。没有实验权限时只提供方案，不声称招募、收费或验证已经完成。

**完成条件**：另一团队能够据此估算和准备实施，但不会误把本次桌面研究当成已完成实验。

### 步骤 10｜审计、写报告和交接

先验证，再压缩，而不是在长报告末尾补一串链接。

1. 对决定性事实逐条回到原文；核验引用真的支持整句话。
2. 对数字重新计算；检查币种、百分比、人数与付费分母。
3. 检查未知和低置信度是否已进入最终结论的限定。
4. 检查报告是否围绕一个决策、三个板块、六个维度，而不是按搜索顺序罗列资料。
5. 更新 `source_stats.json` 或审计结果，明确命中、阅读、引用和原始来源组的不同。
6. 输出 `handoff.md`：已完成、未完成、阻塞原因、下一步可执行动作和关键文件。

报告建议由用户需要决定长度。正文服务决策，细节留附件；不得为了填满模板而编造数据。

**完成条件**：人能读懂，Agent 能接续，证据能追溯，限制没有被藏起来。

## 工作循环与进度沟通

长任务按宿主要求发送简短进展，说明已确认的发现、关键缺口和下一轮目标；不要逐条播报搜索 URL。出现改变方向的证据应及时告知，并附来源。

每次暂停或交接更新状态文件。需要恢复时先读范围、交接和决定性判断，不从头再搜一遍全部材料。动态事实按新访问日重查。

研究结束是因为已足以做受限决策，或明确知道缺什么；不是因为“搜到了 200 个来源”。
