# 06｜从轻断食 APP 案例到通用 Skill

## 1. 这是一份什么性质的复盘

当前对话保留了用户确认的分析框架和已交付的轻断食 APP 报告，但没有可供核验的完整逐次工具日志。

因此，本节可以依据成稿梳理**分析模块与证据用途**，不能声称重放了每一步实际搜索顺序，也不能确认确实深入阅读了“200 多个独立来源”。

下面的执行顺序是为复用而整理的规范顺序。来源台账、自动审计、标准化实验字段和本包脚本是本次新增的控制，不应倒推成上一轮已实际使用。

## 2. 从上一份报告能确认什么

| 成稿里可见的分析模块 | 它服务的问题 | 通用化后的步骤 |
|---|---|---|
| 区分体重管理大需求、采用轻断食、使用工具及付费用户 | 不能把大行业人口直接当品类市场 | 定义范围；D1 分层识别人群 |
| 使用采用行为、商店规模信号和竞争产品 | 品类是否存在，主要供给是什么 | 市场扫描；行为与供给证据线 |
| 区分基础计时和持续执行支持 | 用户到底为什么需要并可能付费 | D2 需求与替代分析；D5 价值机制 |
| 查专业效果与平台限制 | 产品承诺是否适当，实现边界在哪里 | D3 专业/安全与平台约束核验 |
| 明确公司资源未知，不能推定有优势 | 品类成立是否等于公司适合 | D4 能力缺口与条件判断 |
| 列举价格和商业披露，并区分收入口径 | 是否有收费案例，不等于新进入者成功 | 原始来源核验；自述/事实分类 |
| 使用明示假设算转化、获客和贡献 | 经营账需要什么条件才能成立 | 单位经济模型与敏感性分析 |
| 给出窄人群、窄功能的验证建议 | 哪个关键不确定性值得花钱消除 | 最小验证包 |

本节概括的是既有报告内容，不代表本次重新核验了其中所有价格、调查或公司披露。其他 Agent 研究新品类必须重新获取对应证据。

## 3. 不能从成稿确认什么

无法仅凭成稿确认：所有检索词、逐次工具调用、所有打开与失败页面、累计阅读数量、独立来源数量、是否实际执行过代码、是否真的做过产品体验，以及每次改变研究方向的完整记录。

不应该为满足“详细复盘”而补造这些历史。

改进方式是从下一次运行开始实时建立 `actions.jsonl`、`sources.jsonl` 和 `claims.jsonl`，使过程能够由记录支持，而不是依赖事后记忆。

## 4. 本次新增的操作控制

| 新增控制 | 解决的问题 |
|---|---|
| 范围与公司输入模板 | 防止无边界搜索和虚构公司能力 |
| 决定性问题与反证优先级 | 防止资料很多却不改变决策 |
| 工具能力映射与访问状态 | 防止假装使用未连接数据源 |
| 来源组、阅读状态和动作日志 | 防止把命中或转载当成独立阅读 |
| 判断分类与口径字段 | 防止把假设写成事实、把不同指标混算 |
| 六维结论卡 | 防止报告重新退化为无层级字段堆砌 |
| 经营模型脚本和边界条件 | 防止除零、漏项、错误复算和无依据乐观预测 |
| 样本解释与验证模板 | 防止把小规模探索说成商业模型已验证 |
| 质量审计和交接约定 | 让其他 Agent 能复核并继续工作 |

## 5. 应复用和不应复用的内容

**应复用**：一个最终决策、三个判断板块、六个维度；先定性再可靠定量；每个判断有证据和把握；最后把未知变成验证任务。

**不应复用**：轻断食的具体人群假设、竞争样本、价格、预算、付费比例、健康边界细节以及“值得”的结论。其他品类可能最终得到“不值得”或“证据不足”。

**尤其不要把“AI 陪伴”做成任何 APP 品类的默认答案。**先找用户任务、替代方案和付费理由，再判断是否需要 AI；AI 可以是实现方式，不能代替市场证据。

## 6. 这套流程真正复用的是什么

不是“每个品类搜索很多网页”，而是：

> 用最重要的问题决定查什么；用原始证据限制结论；用经营账找出成立条件；用最小验证包消除剩下的关键未知。

人看到的是简洁决策，后续 Agent 看到的是能够继续执行、能够核验的工作底稿。
