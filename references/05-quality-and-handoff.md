# 05｜质量控制、分工、恢复与交付

## 1. 两种检查，不得混为一谈

**机械检查**能检查文件格式、必填字段、ID 引用、重复来源定位、缺失公式及六维覆盖。

**实质检查**才回答：引用是否真的支持判断，比较口径是否适用，反证是否充分，公司能力是否被猜测，经营模型是否遗漏主要成本。

`audit_research.py` 只做前者并给出警告。任何 Agent 都不得写“脚本通过，因此所有来源与结论均准确”。

## 2. 交付前的人工检查清单

### 决策与结构

1. 首句是否回答“值不值得出最小验证包”，而不是给行业百科？
2. 是否固定三个板块、六个维度，研究方法没有被误排为新维度？
3. 结论是否针对明确人群、场景、地区和公司条件？
4. 是否区分市场吸引力、公司适配和经营成立，避免互相代替？

### 证据与口径

5. 决定性事实是否全部有实际读过且可定位的证据？
6. 当前价格、产品功能、平台费率、政策及趋势是否按本轮日期核验？
7. 公司披露、第三方估算、我们的模型假设是否明确归属？
8. 是否混淆下载、月活、评分、付费、营收、ARR、净利润？
9. 地区、时间、人群、单位、平台、统计分母是否匹配？
10. 同源转载是否被错误当成多方验证？来源数量是否来自真实日志？
11. 重要冲突和相反证据是否被保留，低把握是否传递到最终建议？
12. 未知是否仍为未知，而不是变成零、默认中等分或未经证实的优势？

### 经营与验证

13. 计算是否可复算，主要成本是否包括，现金回款与利润是否分开？
14. 获客和付费是否属于同一批人、同一渠道和同一观察窗口？
15. 是否依赖未实测的续费、免费自然流量或多个同时乐观假设？
16. 最小验证包是否有明确假设、实际行为、窗口、预算和继续/停止条件？
17. 小样本是否只得出其能够支持的探索性结论？
18. 健康等高风险品类是否有专业证据和安全边界，未经授权的执行是否被避免？

### 可交接性

19. 每条决定性推断是否能回到前提判断，估算是否能回到输入和公式？
20. 下一位 Agent 是否知道哪些已完成、哪些未完成、被什么阻塞、下一步读哪个文件？

失败项按严重程度修复。决定性引用错误、虚构公司能力和把假设写成事实必须修正；资料客观缺失则限制结论并明确交接，不为了通过清单捏造内容。

## 3. 红队检查：从最强反对意见开始

让第二位 Agent 或同一 Agent 的独立复核步骤回答：

```text
假设这份建议是错的，最可能错在哪个关键前提？
如果只允许再读三份来源，应读什么，为什么？
有没有替代解释同样能说明观察到的数据？
最终建议是否比证据实际允许的更强？
```

输出不是情绪化反对，也不是重新写一篇报告，而是：`争议判断 ID → 反证或缺口 → 对决策的影响 → 建议修正`。

例如“竞品有付费套餐”只证明商品供给存在，不证明转化良好；“公司自述收入高”可能证明商业模式有案例，但不能自动代表品类盈利水平。

## 4. 多 Agent 分工：按证据线并行，主 Agent 统一判断

仅在宿主真实支持且授权允许时启动并行。没有此能力就按同样角色顺序执行，不谎称已调用子 Agent。

可采用三条研究线和一次复核：

| 角色 | 任务 | 统一交付 |
|---|---|---|
| 市场与用户研究 | D1、D2：范围、行为、需求与替代 | 来源、判断、口径、缺口 |
| 产品与公司研究 | D3、D4：实现依赖、专业边界、公司资产 | 来源、判断、能力缺口 |
| 商业与竞争研究 | D5、D6：价格、模式、经营参数与竞争 | 来源、判断、情景输入 |
| 主 Agent/复核者 | 统一定义、核对冲突、建模、反证、最终决策 | 总结、审计和交接 |

所有研究者共享相同 `brief.json`、问题 ID、时间基准、口径和证据规范。来源 ID 可加角色前缀以避免碰撞，合并时保留旧 ID 映射。

分工指令必须包含：回答哪些问题、不回答什么、优先来源、允许工具、预算或权限限制、输出格式和停止条件。不能只说“帮我深入研究市场”。

合并时检查：同源去重、产品实体对齐、不同地区分离、数字口径、重复引用和互相矛盾的假设。多个 Agent 引用同一份新闻稿仍是一条原始证据，不是多方独立支持。

## 5. 断点恢复与增量调研

每个运行使用独立目录，避免新旧数据混入。暂停前更新 `handoff.md`：

- 范围与当前阶段。
- 已完成的决定性判断及其证据 ID。
- 未完成问题、失败原因和下一步动作。
- 临时假设、待刷新数据、文件位置与模型版本。
- 是否已进行真实实验；没有则明确未进行。

恢复顺序：先读 brief 和 handoff → 读六维结论及决定性 claims → 补必要来源 → 执行下一步。不要从头无差别重搜。

更新研究时，旧资料保留访问日期与历史状态；新值另记并说明变化。不能覆盖旧记录而丢失当时判断依据。

## 6. 报告结构与层级

正文固定：

```text
一句最终决策及限制
三个板块摘要
研究范围与口径
A 机会好不好：D1 + D2
B 我们能不能做：D3 + D4
C 能不能经营好：D5 + D6
最小验证包或不投入理由
决定性未知与重新考虑条件
```

证据表、竞品表、模型和来源放在它们支撑的段落附近；过细台账放附件。不额外添加 SWOT、PEST、五力、增长飞轮等并列框架，除非某个工具确实帮助回答现有维度中的问题。它们应是局部分析工具，不是新的报告主干。

不要反复重复同一句最终判断。结论在顶部完整表达，文末只收束关键条件。

## 7. 交付物最小集合

| 文件 | 谁使用 | 用途 |
|---|---|---|
| `report.md` | 决策者 | 结论、理由、限制、行动 |
| `brief.json` + `research_plan.md` | 后续 Agent | 范围和问题树 |
| `sources.jsonl` + `claims.jsonl` | 审核者/后续 Agent | 证据追溯与置信度 |
| `dimension_assessments.json` | 主 Agent | 六维到决策的压缩层 |
| `unit_economics.json` + 计算结果 | 经营分析者 | 假设与成立条件 |
| `validation_package.md` | 执行团队 | 下一轮要验证什么 |
| `actions.jsonl` + `audit.json` | 复核者 | 可观察动作与结构检查 |
| `handoff.md` | 接手 Agent | 当前状态与下一步 |

可以合并不必要的空文件，但不能丢失这些信息。市场资料不足时，交付明确的不足和补证路径，比输出一份伪完整报告更好。

## 8. 更新 Skill 自身

每完成一个新品类，保留失败模式和用户纠正，不将该品类的数字硬编码到通用主文件。更新版本、改变原因、受影响步骤与回归用例。

优先修复实际出现的错误：指标混用、假装访问、公司优势虚构、忽略替代品、过早承诺盈利。不要每次增加一套新的框架，让 Skill 再次变成字段堆砌。

使用 `tests/agent_eval_cases.md` 实跑后记录通过和失败。仅阅读测试说明不算完成 Agent 回归。
